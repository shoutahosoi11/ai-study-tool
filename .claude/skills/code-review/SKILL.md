# Code Review Skill

このスキルは、コード・差分・Pull Request をレビューするためのものです。  
単なる感想ではなく、バグ、設計、保守性、規約準拠まで含めて評価してください。

## レビューの基本方針

- まず変更の目的を推定する
- その変更が要件に対して妥当か確認する
- その上で、バグ・設計・保守性・テスト観点をレビューする
- 指摘は「本当に重要なもの」を優先する
- スタイルの好みより、正しさ・安全性・保守性を優先する
- 改善点がある場合は、可能なら具体的な修正方針まで示す
- 必要以上に細かい指摘を増やさず、優先順位をつける

## 優先順位

以下の順で重要度を判断する。

1. ランタイムエラー、panic、nil参照、未定義動作
2. データ不整合、トランザクション境界の誤り、排他制御ミス
3. 認証・認可漏れ、情報漏洩、インジェクションなどのセキュリティ問題
4. Clean Architecture違反、責務分離の崩れ、依存方向の破壊
5. API仕様不整合、レスポンス形式の揺れ、バリデーション漏れ
6. テスト不足、異常系未検証
7. 可読性、命名、重複、軽微な改善点

## このリポジトリで特に見る観点

このプロジェクトでは、以下を重点的に確認すること。

### 1. Clean Architecture / レイヤー構造

依存関係は以下を守ること。

- handler → usecase → domain ← infrastructure

確認項目:

- handlerにビジネスロジックが入っていないか
- usecaseから直接DBや外部APIを触っていないか
- domainにDBタグ、JSONタグ、外部依存が入っていないか
- infrastructureがdomainのinterfaceを実装しているか
- main.goに依存関係が集中しすぎていないか

### 2. Go バックエンド規約

- GORMは禁止。sqlcを優先する
- sqlcが使えない場合のみ限定的にdatabase/sqlを使う
- Goはfunction宣言を基本とし、無名関数の乱用を避ける
- context.Contextが必要な層では第一引数に渡されているか
- errorは握りつぶさず、wrapして返しているか
- panicを使っていないか
- nil, nil のような危険な返し方をしていないか

### 3. DB / SQL / Repository

- N+1が起きていないか
- select対象やwhere条件が妥当か
- paginationのlimit/offset/page計算にミスがないか
- CountとListが必要なら両方揃っているか
- トランザクション境界が妥当か
- transaction内で外部APIを呼んでいないか
- repository層にSQL詳細が閉じているか
- upsertやdeleteの冪等性が要件に合っているか

### 4. 認証・認可

- 認証必須のAPIが素通りしていないか
- middleware初期化失敗時にfail-openになっていないか
- userID取得が安全か
- 他人のデータを読めたり削除できたりしないか

### 5. API設計

- HTTPメソッドが自然か
- 404/400/401/500/502の使い分けが妥当か
- レスポンス形式が既存ルールに揃っているか
- request/response DTO と domain が分離されているか
- バリデーションがhandlerまたはDTO境界で行われているか

### 6. フロントエンド規約

- JavaScript / TypeScript はアロー関数を使わず、function宣言を使っているか
- UIコンポーネントに色・余白・フォントを直書きしていないか
- デザイン値が theme に集約されているか
- フロントエンドに業務ロジックを持たせすぎていないか
- API通信が api 層に閉じているか
- loading / error / empty state が考慮されているか
- 認証を自前実装していないか

### 7. テスト

- usecaseレイヤーのユニットテストがあるか
- 正常系だけでなく異常系も見ているか
- 外部依存がinterface経由でモック可能になっているか
- テストしにくい設計になっていないか

## セキュリティ観点

以下は必ず確認する。

- SQL injectionの危険
- XSSの危険
- 認証・認可漏れ
- secretsやAPIキーのハードコード
- 個人情報をログ出力していないか
- 無制限なCORS設定になっていないか

## パフォーマンス観点

以下は必要に応じて確認する。

- 不要なDBクエリがないか
- 不要なループやネストがないか
- 不必要なgoroutine生成がないか
- 並列処理が安全か
- 共有変数の競合やcontext cancel漏れがないか

## レビュー時の振る舞い

- まず変更の意図を1〜3文で要約する
- その後、重大な問題から順に指摘する
- 重大な問題がなければ、そのことを明示する
- 軽微な改善は「すぐ直すべきか」「後続PRでよいか」を分ける
- 指摘には理由を書く
- 可能なら修正案を書く
- 不確実な点は断定せず、Questionsに出す

## 出力フォーマット

以下の形式で出力すること。

### Summary
- この変更が何をしようとしているかを短く要約

### Good
- 良い点を箇条書き
- 設計や実装で妥当な点を明示

### Needs Improvement
- 改善点を箇条書き
- 重要な順に並べる
- 各項目に「なぜ問題か」を書く
- 可能なら具体的な修正案を書く

### Questions
- 不明点
- 要件次第で判断が変わる点
- バックエンド仕様やAPI仕様の確認が必要な点

## 厳しさの基準

以下は強く指摘すること。

- authのfail-open
- transaction境界の誤り
- domainへの外部依存混入
- handlerへのビジネスロジック混入
- API仕様不整合
- nil/error handlingの危険
- 重大なセキュリティ問題

以下は軽微なら提案レベルに留めること。

- 命名の細かな好み
- コメントの書き方
- 些細な整形
- 今すぐ壊れない軽微な重複

## 最後の原則

- 動くことだけでなく、保守できることを重視する
- ただし、改善のために変更を止めすぎない
- 即時対応が不要な改善は、後続PRでもよいと明示する
