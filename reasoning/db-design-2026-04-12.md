## 機能要件

### 1. 学習データとユーザーデータを分離しつつ関連付ける
- 要件:
  ユーザー、書籍、興味分野、ハイライト、ノート、問題、回答、投稿、ソーシャル反応をそれぞれ別の責務として保持する。
- 意図:
  学習コンテンツとユーザー行動ログを後から拡張しやすくする。

### 2. 同じユーザー操作を冪等に扱えるようにする
- 要件:
  フォロー、いいね、リポスト、回答保存などは、同じ操作が重なってもデータ破壊や重複登録を起こさない。

### 3. タイムライン取得を現実的なクエリコストで返す
- 要件:
  follow、book、interest の複数関係を使って投稿を集め、関連スコア順と新着順で返せること。

### 4. 学習進捗と採点結果を保存できる
- 要件:
  問題回答を再提出しても最新値へ更新し、必要な統計値を保持できること。

## 非機能要件

### 1. データ整合性
- 外部キーで参照整合性を維持する
- 重複登録を主キーや unique 制約で防ぐ
- 更新系は必要に応じて transaction でまとめる

### 2. 性能
- タイムラインや一覧取得でテーブルフルスキャンを避ける
- JOIN 用のキーと並び順に合わせた index を置く
- カウント系は毎回集計せず、必要に応じて保持値を持つ

### 3. 保守性
- テーブル責務を分ける
- SQL は repository 層へ閉じる
- PostgreSQL の素直な機能で構成し、特殊な DB 依存を増やしすぎない

### 4. セキュリティ
- ユーザーデータ取得時はログインユーザー確認と認可確認を行う
- 直接他人の行動データへアクセスできないようにする

## 技術・構成判断ごとの理由とトレードオフ

### 判断1. RDB として PostgreSQL を使う
- なぜこの技術を選んだか:
  ユーザー、投稿、問題、回答、ソーシャル関係のように関連が多いデータを整合性付きで扱いたかったから。
- 他の選択肢とのトレードオフ:
  NoSQL は柔軟だが、多対多や集計付き JOIN を扱うと整合性とクエリ設計が難しくなりやすい。
- メリット:
  - 外部キーと unique 制約で整合性を守りやすい
  - JOIN ベースの timeline SQL を組みやすい
  - transaction を素直に扱える
- デメリット:
  - スキーマ変更の計画が必要
  - 書き込みパターンによっては設計を誤ると重くなる

### 判断2. 主キーに UUID を使う
- なぜこの技術を選んだか:
  分散生成しやすく、クライアントや複数サービスとの境界でも扱いやすいから。
- 他の選択肢とのトレードオフ:
  bigint の連番は軽いが、予測しやすく、外部露出時に列挙されやすい。
- メリット:
  - 外部公開 ID として扱いやすい
  - 連番漏えいを避けやすい
  - オフライン生成もしやすい
- デメリット:
  - index サイズは大きくなりやすい
  - 人間が読みづらい

### 判断3. users / books / fields を分け、user_books / user_interests を中間テーブルで正規化する
- なぜこの構成を選んだか:
  ユーザーと書籍、ユーザーと興味分野は多対多関係であり、1テーブルへ詰めると更新と検索が崩れるから。
- 他の選択肢とのトレードオフ:
  配列カラムや JSONB に埋め込む方法は実装は速いが、JOIN と制約、集計が弱くなる。
- メリット:
  - 正規化される
  - 多対多の検索や集計がしやすい
  - unique 制約や外部キーを貼りやすい
- デメリット:
  - JOIN 数は増える
  - 単純参照でも中間テーブルが必要になる

### 判断4. social 系は関係テーブルを正規化し、posts にカウンタを非正規化で持つ
- なぜこの構成を選んだか:
  likes / reposts / comments の真実のデータは個別テーブルに持ちつつ、一覧表示で毎回 COUNT しないように `posts.like_count` などを保持したかったから。
- 他の選択肢とのトレードオフ:
  完全正規化で毎回 COUNT する方法は整合性は素直だが、タイムラインの読取コストが上がる。
- メリット:
  - 一覧取得時の表示が速い
  - 反応テーブルの真実データも残る
  - ソーシャル操作は `ON CONFLICT DO NOTHING` と相性がよい
- デメリット:
  - カウンタ更新漏れのリスクがある
  - transaction 設計を誤ると実数とズレる

### 判断5. answers は `(user_id, question_id)` の upsert を使う
- なぜこの構成を選んだか:
  同じ問題への再回答を最新状態で保存したかったから。
- 他の選択肢とのトレードオフ:
  回答履歴を全件保持する設計は分析には強いが、現在値の取得と UI 表示が少し重くなる。
- メリット:
  - 冪等に扱いやすい
  - 最新回答を取り出しやすい
  - API と整合しやすい
- デメリット:
  - 回答履歴をそのままは残せない
  - 分析用途では別テーブルが必要になるかもしれない

### 判断6. timeline 用 SQL は application 側でスコアリング付き CTE を使う
- なぜこの構成を選んだか:
  follows、user_books、user_interests の複数関係を1回のクエリでまとめたかったから。
- 他の選択肢とのトレードオフ:
  アプリ側で複数クエリを投げてマージする方法は分かりやすいが、N+1 やデータマージ複雑化を招きやすい。
- メリット:
  - 1クエリで順位付けまでできる
  - DB が得意な JOIN と集約に寄せられる
  - API 返却までが素直
- デメリット:
  - SQL が複雑になる
  - index 戦略が重要になる

### 判断7. posts テーブルに複数 nullable FK を置く
- なぜこの構成を選んだか:
  post が question 起点、note 起点、book 起点、field 起点のどれでも作れる多態的な性質を簡単に表現したかったから。
- 他の選択肢とのトレードオフ:
  完全な polymorphic table や type ごとの投稿テーブル分割もあるが、取得系が分かれやすい。
- メリット:
  - 1つの posts テーブルに集約できる
  - timeline や social とつなぎやすい
  - API 層では扱いやすい
- デメリット:
  - nullable column が増える
  - `type` と FK の整合性を DB 制約で完全には表しにくい

### 判断8. index はまず query 起点で必要最小限に置く
- なぜこの構成を選んだか:
  timeline、answers、highlights など、まず遅くなりやすい読取に効く index から優先したかったから。
- 他の選択肢とのトレードオフ:
  先回りして index を大量に貼ると、書き込み性能と運用負荷が悪化しやすい。
- メリット:
  - 実クエリに沿った最小構成にできる
  - index メンテナンスコストを抑えやすい
- デメリット:
  - 後から追加 index が必要になることがある
  - 想定外クエリには弱い

## 具体的に見た SQL / スキーマから読み取れる設計意図

### users
- `firebase_uid` と `username` に unique 制約がある
- 認証系の主キーは Firebase UID、内部参照や外部キーは UUID に分けている

### posts
- `like_count` / `repost_count` / `comment_count` は非正規化カウンタ
- `question_id`, `note_id`, `book_id`, `field_id` が nullable で、多態的投稿モデルを作っている

### follows / likes / reposts
- 複合主キーで重複登録を防いでいる
- repository でも `ON CONFLICT DO NOTHING` を使い、API 冪等性を強めている

### answers
- `(user_id, question_id)` upsert を使い、再回答時は `updated_at` を更新している
- `UpsertAndUpdateStats` では transaction を使って回答保存と問題統計更新をまとめている

### timeline SQL
- CTE `scored` で follow/book/interest の優先度を score 化
- その後に posts, users, books, fields と JOIN して API 表示用の shape を作っている

## 他の選択肢と比べたときの DB 設計上の大きな論点

### 正規化をもっと強くする案
- 例:
  投稿カウンタを持たず、毎回 likes / reposts / comments を集計する
- 良い点:
  真実のデータは1箇所になる
- 悪い点:
  一覧表示が重くなりやすい

### 非正規化をもっと強くする案
- 例:
  タイムライン用の派生テーブルや materialized view を前計算する
- 良い点:
  読み取りは速い
- 悪い点:
  更新と整合性維持が難しくなる

### JSONB に寄せる案
- 例:
  post の関連先を JSON に埋める
- 良い点:
  スキーマ変更が楽
- 悪い点:
  外部キー制約や JOIN 最適化が弱くなる

## システム全体でどこが難しかったか
- 正規化しすぎると読み取りクエリが重くなる点
- 非正規化しすぎると整合性維持が難しくなる点
- post の多態性を 1 テーブルに寄せつつ、timeline を破綻なく返す点
- social カウンタを transaction 内で安全に更新する点

## どう切り分けて考えたか
1. 真実のデータはどこに置くかを決める
2. 一覧表示のために派生値が必要かを切り分ける
3. 冪等操作かどうかを決める
4. transaction が必要な更新単位を決める
5. 実際の repository SQL に必要な index を切り出す

## どう調べてどう前に進んだか
- migration ファイルを確認して、テーブル、外部キー、index を洗い出した
- `post_repository.go` を見て、timeline がどの JOIN と並び順に依存しているか確認した
- `social_repository.go` を見て、関係テーブルと非正規化カウンタの組み合わせ方を確認した
- `answer_repository.go` を見て、upsert と transaction の単位を確認した

## その結果何が変わったか
- この DB は「基本は正規化、表示高速化が必要な一部だけ非正規化」という方針で整理できた
- social 系の冪等性が DB 制約と SQL の両方で支えられていることが明確になった
- post の多態性と timeline SQL の複雑さが、設計上の主要トレードオフだと明確になった

- answers の履歴保持が必要なら current table と history table を分ける
