# Database Setup Rationale (Current)

## 現在の前提

- 本番 DB は Neon PostgreSQL を使う。
- Cloud Run からは `DATABASE_URL` で接続する。
- ローカル開発は `docker-compose.yml` の PostgreSQL 16 を使う。
- `backend/db/migrations/030_add_user_daily_generation_count.sql` までが現行スキーマ。

## ローカル開発の考え方

ローカルでは Docker の PostgreSQL 16 を使い、アプリコードは本番と同じ `DATABASE_URL` 形式で接続する。Neon と同じ PostgreSQL 系を使うことで、SQL 方言差分を持ち込まずに開発できる。

### 理由

- `sqlc` と `database/sql` の組み合わせは PostgreSQL の素直な挙動に寄せた方が安全。
- 本番だけ Neon 固有の分岐を持ち込むより、接続先だけ差し替える方が保守しやすい。
- question sync のトランザクションや `FOR UPDATE SKIP LOCKED` をローカルでも再現しやすい。

## 本番デプロイの考え方

本番は Cloud Run + Neon を前提にする。Cloud SQL connector や Cloud SQL Auth Proxy は使わない。GitHub Actions から Cloud Run へデプロイし、`DATABASE_URL` と `GEMINI_API_KEY` は Secret Manager から注入する。

### 理由

- 現在の運用前提が Neon なので、ドキュメントも Neon を基準に統一した方が混乱が少ない。
- Cloud Run 側では DB 接続文字列だけ知っていればよく、インフラ差分をアプリ内へ持ち込まなくて済む。

## テスト用 DB

統合テストは `INTEGRATION_DATABASE_URL` を使う。これはローカル PostgreSQL 16 でも Neon の検証用 DB でもよい。

### 想定用途

- `question_sync_repository_integration_test.go`
- トランザクション境界の確認
- stale processing の再キュー確認
- 日次上限カウンタと queue の整合性確認

## マイグレーション運用

- ローカル Docker でも Neon でも、`backend/db/migrations/*.sql` を番号順に適用する。
- question sync を有効にする本番環境では `030_add_user_daily_generation_count.sql` が必須。
- 既存の reasoning にある「Docker が起動しなかった実行ログ」は履歴としては意味があるが、現在のセットアップ方針ではない。

- 本番前提は Neon、ローカル前提は Docker PostgreSQL 16 に統一する。
