# AI Consensus Review とシステム要件メモ

## このメモで保存する内容
今回の会話で出た要望を、実装済み項目と今後の要件に分けて保存する。

対象は2つある。

1. Codex と Claude を使ったローカルの合意形成レビュー自動化
2. システム全体に求める運用・セキュリティ・保存方針

## いま反映したこと
- Codex と Claude の両方に同じ diff をレビューさせるスクリプトを追加した
- 両者のレビュー結果をさらに相互評価させて、双方が agree した指摘だけを抽出するようにした
- `--apply` を付けたときだけ、合意した指摘に基づく修正を Codex に依頼する形にした
- `--changed-under backend/internal` のように、複数ファイルをディレクトリ単位で順番に処理できるようにした
- `--changed-under` を複数回指定したときは、その指定順を保って処理するようにした
- Claude の認証切れ、トークン枯渇、予算・利用上限っぽい失敗を検出したら workflow を `paused` にして止めるようにした
- レビュー時の prompt、stdout、stderr、summary、status を `.ai-consensus/` 配下へ保存するようにした
- pause 後の再開では、同じファイルの保存済み `codex_review.json` や `codex_consensus.json` を再利用し、完了済み段階をやり直さず続きから進めるようにした

## 機能要件

### 1. Claude のトークンや認証が切れたら一時停止する
- 要件:
  Claude 側のレビューや合意フェーズで、認証切れ、API key 問題、クレジット不足、利用上限などが疑われる失敗が起きたら、workflow を失敗扱いではなく `paused` にする。
- 期待動作:
  - 途中までの成果物を残す
  - `status.json` と `summary.md` に paused 理由を書く
  - 修正適用フェーズには進まない

### 2. データ取得時はログインユーザー確認を必須にする
- 要件:
  データを返す API は、対象データに対して現在のログインユーザーが参照可能かを確認する。
- 対象:
  - 自分専用データの取得
  - 更新・削除系 API
  - 将来の会話履歴ファイル参照やレビュー履歴参照
- 補足:
  これは「認証済みか」だけではなく、「そのユーザーがそのデータへアクセスしてよいか」の認可確認を含む。

### 3. 画像やファイルのアップロードは SaaS ビルダー標準機能を優先する
- 要件:
  画像などのアップロード機能は、料金のかからない SaaS 型ビルダーやプラットフォームが提供する規定の仕組みに載せる。
- 意図:
  独自のアップロード基盤、独自署名 URL サービス、独自ストレージ中継 API を増やしすぎない。

### 4. 会話内容やレビュー履歴をファイルとして保存する
- 要件:
  レビュー対象、レビュー prompt、応答、合意結果、適用結果、運用メモをファイルとして残す。
- 期待動作:
  - 再現できる
  - 後から判断理由を追える
  - Claude 側が途中停止しても、どこまで進んだか分かる

## 非機能要件

### 1. コスト管理
- Claude 側で利用枯渇が起きたら処理を止める
- 無料で使える標準機能を優先する
- 高コストな外部依存を増やす前に代替案を比較する

### 2. セキュリティ
- データ取得時にログインユーザー確認を必須にする
- レビュー結果や会話ログにも機密情報を残しすぎない
- アップロード経路はプラットフォーム標準の認可に載せる

### 3. 可観測性
- これは開発中のローカルデバッグログではなく、本番運用時のアクセス監査と不審アクセス対策を指す
- アクセスログとエラーログは保存先を分ける
- アラート条件を定義する
- 認証失敗、認可失敗、不審アクセス傾向を運用イベントとして見えるようにする

### 4. 監査性
- いつ、どの diff に、どの prompt を使い、何に合意したか追跡できること
- 人間が最終判断したかどうかも追えること

## ログとアラート要件

ここでいうログは、開発時の一時的な標準出力やローカルデバッグ用途ではなく、本番運用での監査・セキュリティ対策・障害対応のためのログを指す。

### アクセスログ
- 保存対象:
  - 誰がいつどの API やリソースへアクセスしたか
  - 認証されたユーザー ID
  - 対象リソース ID や操作種別
  - 送信元 IP や User-Agent など、不審アクセス判定に必要な最小限の情報
  - 成功 / 失敗 / 拒否
- 保存先:
  エラーログと分離する。監査用途の保存先へ送る。

### エラーログ
- 保存対象:
  - バックエンド例外
  - ストレージやアップロード処理失敗
  - 5xx 応答
  - 外部サービス失敗
- 保存先:
  アクセスログと別にする。障害調査用の保存先へ送る。

### アラート
- 最低限ほしいアラート:
  - 認証系 401/403 増加
  - 同一ユーザーや同一 IP による異常な連続失敗
  - 特定リソースへの不自然な集中アクセス
  - 権限外データへのアクセス試行
  - アップロード失敗率増加
  - バックエンド 5xx 増加

## 技術・構成判断ごとの理由とトレードオフ

### 判断1. 2つの AI を直接会話させず、オーケストレータ方式にした
- なぜこの構成を選んだか:
  自由会話型よりも、同じ diff を両者へ配り、JSON を集めて機械判定する方が再現性が高いから。
- 他の選択肢とのトレードオフ:
  直接対話型は自然な議論ができるが、結論の抽出が不安定になりやすい。
- メリット:
  - 判断基準を固定しやすい
  - 合意条件をコードで書ける
  - ログを残しやすい
- デメリット:
  - やや機械的
  - 相互補完の自然な会話は起きにくい

### 判断2. Claude 側のトークン・認証・予算問題では failed ではなく paused にした
- なぜこの構成を選んだか:
  利用枯渇はコード不正ではなく運用上の一時停止として扱った方が再開しやすいから。
- 他の選択肢とのトレードオフ:
  すべて failed にすると単純だが、再実行時の文脈や途中成果が埋もれやすい。
- メリット:
  - 再開判断がしやすい
  - 原因が明確
  - apply の誤実行を防げる
- デメリット:
  - paused 判定キーワードの保守が必要
  - 完全な原因判定ではなく推定を含む

### 判断3. レビュー結果を JSON Schema で固定した
- なぜこの構成を選んだか:
  互いの結果を比較して合意判定するために、構造化出力が必要だったから。
- 他の選択肢とのトレードオフ:
  自由文レビューは読みやすいが、差分抽出や自動適用への接続が難しい。
- メリット:
  - 自動処理しやすい
  - finding 単位で相互評価できる
  - ファイル保存に向く
- デメリット:
  - 表現力が下がる
  - CLI ごとの JSON 出力安定性に依存する

### 判断4. 会話内容と判断材料を `.ai-consensus/` に保存するようにした
- なぜこの構成を選んだか:
  後で「何を根拠にその変更をしたか」を追えるようにしたかったから。
- 他の選択肢とのトレードオフ:
  何も保存しない方が軽いが、再現性と監査性を失う。
- メリット:
  - デバッグしやすい
  - 監査しやすい
  - チームで振り返りやすい
- デメリット:
  - 保存量が増える
  - 秘匿情報の扱いに注意が必要
- 補足:
  これは AI レビュー workflow 自体の成果物保存の話であり、本番運用のアクセス監査ログとは別物である。

### 判断5. `--apply` は双方合意した指摘があるときだけ動かす
- なぜこの構成を選んだか:
  一方だけの指摘で自動変更すると誤修正のリスクが高いから。
- 他の選択肢とのトレードオフ:
  片方のレビューだけで即時適用すると速いが、誤爆が増える。
- メリット:
  - 自動変更の安全性が上がる
  - 人間の心理的負担が下がる
- デメリット:
  - 保守的になる
  - 正しい指摘でも片方が見落とすと適用されない

### 判断6. データ取得時のユーザー確認を必須要件として明記した
- なぜこの構成を選んだか:
  認証済みと認可済みは別であり、ログイン済みでも他人のデータを返してはいけないから。
- 他の選択肢とのトレードオフ:
  認証だけで通す実装は簡単だが、将来的な情報漏えいリスクが高い。
- メリット:
  - 認可漏れを防ぎやすい
  - API 単位で責務を明確にしやすい
- デメリット:
  - 実装箇所が増える
  - テスト観点が増える

### 判断7. アップロード機能はプラットフォーム標準機構に寄せる
- なぜこの構成を選んだか:
  コストと運用負担を抑えたいから。
- 他の選択肢とのトレードオフ:
  独自アップロード基盤は柔軟だが、実装・監視・セキュリティ負担が増える。
- メリット:
  - 低コスト
  - 早く作れる
  - セキュリティ責務を減らせる
- デメリット:
  - カスタマイズ性は下がる
  - プラットフォーム制約を受ける

### 判断8. 本番運用ではアクセスログとエラーログを分離する
- なぜこの構成を選んだか:
  不審アクセス検知と障害調査では、見るべき情報と保存要件が異なるから。
- 他の選択肢とのトレードオフ:
  1つのログ基盤に全部混ぜると実装は単純だが、監査と障害解析の両方でノイズが増える。
- メリット:
  - セキュリティ監査しやすい
  - アラート条件を分けやすい
  - 障害調査時の検索性が上がる
- デメリット:
  - ログ設計が少し増える
  - 保存先や保持期間の設計が必要

### 判断9. 複数ファイル処理は「ファイル単位の順次実行 + attempt 保存」にした
- なぜこの構成を選んだか:
  `backend/internal` 全体のような広い対象でも、どのファイルまで終わってどこで止まったかを追えるようにしたかったから。
- 他の選択肢とのトレードオフ:
  全ファイルを1回の大きなレビュー対象にすると一括感はあるが、途中停止時に再開粒度が粗くなり、どこまで終わったか管理しにくい。
- メリット:
  - 再開位置が明確
  - 失敗範囲をファイル単位に閉じ込めやすい
  - レポートを見返しやすい
- デメリット:
  - レポートディレクトリ数が増える
  - ファイルをまたぐ指摘は弱くなりやすい

### 判断10. `--changed-under` の指定順をそのまま処理順に使う
- なぜこの構成を選んだか:
  Clean Architecture の層順や、`middleware -> handler -> usecase` のような人間の修正順に合わせて動かしたかったから。
- 他の選択肢とのトレードオフ:
  変更ファイルを単純にファイル名順で回す方が実装は単純だが、設計上の依存順を無視しやすい。
- メリット:
  - 意図した順番で修正を進めやすい
  - レイヤー単位で pause / resume を考えやすい
  - ユーザーの作業順と揃えやすい
- デメリット:
  - prefix が重なると順序ルールを理解しておく必要がある
  - 完全な依存解析ではなく、あくまで人が指定した順番に従う方式である

## システム全体でどこが難しかったか
- 2つの異なる CLI を、同じ基準で比較可能なレビュー結果に揃えるところ
- AI の失敗を「コード不正」と「運用停止」に分けて扱うところ
- 自動変更まで進める場合に、どこで止めると安全かを決めるところ

## どう切り分けて考えたか
1. diff を集める
2. 各 AI に同じ条件でレビューさせる
3. finding を構造化する
4. 相互評価させる
5. 双方 agree のものだけ抽出する
6. そこで初めて apply を許可する
7. 失敗系は failed と paused に分ける

## どう調べてどう前に進んだか
- `codex --help`, `codex exec --help`, `codex review --help` を確認して、非対話実行と schema 出力の扱いを調べた
- `claude --help` を確認して、非対話実行、JSON schema、tool 無効化の方法を確認した
- 既存リポジトリ内の `reasoning/` を見て、このプロジェクトの設計メモの残し方を合わせた
- まずはスクリプト、次に VS Code task、最後にドキュメントという順番で進めた

## その結果何が変わったか
- レビューのたびに手動で両 AI へ同じ説明を繰り返す必要が減った
- Claude 側の認証や予算問題で止まっても、途中成果を残したまま safely pause できるようになった
- どの判断をなぜ採ったかを、会話に依存せずファイルで残せるようになった
- 本番運用のセキュリティ要件として、認可確認、ログ分離、アラート、アップロード方針を明示的に切り出した
