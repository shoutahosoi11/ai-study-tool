# 問題解答API 設計根拠

## FOR UPDATEを使わずアトミック更新にした理由
`SELECT → +1 → UPDATE` のパターンはTOCTOU（Time-of-Check-Time-of-Use）競合が発生する。
複数リクエストが同時に同じ問題の統計を取得すると、同じ値を読んで+1して書き込み、
結果として1件分しかカウントされない。

`UPDATE questions SET answer_count = answer_count + 1 WHERE id = $1` はDB側でアトミックに
実行されるため、SELECT不要・ロック不要で正確にカウントできる。

## トランザクション外でLLMを呼ぶ理由
LLMの応答には数秒かかる。トランザクション内で外部APIを呼ぶと：
- トランザクションがロックを保持したまま数秒待機
- 同一行を更新しようとする他のリクエストがブロックされる
- デッドロックのリスクが高まる

解決策: LLM呼び出しをトランザクション外で行い、結果取得後にDBへ書き込む。
Upsertと統計更新は各々アトミックなSQLのため、トランザクションなしで安全。

## context.Contextを引き回す理由
LLMの応答が遅い場合（タイムアウト）やクライアントが通信を切断した場合に、
context.Cancelが伝播して即座に処理をキャンセルしリソースを解放するため。
Handler → Usecase → Repository, LLMClient まで全レイヤーでctxを第一引数で渡す。

## 選択問題と記述問題の判定方法の違い
- 選択問題: `question.CorrectAnswer == userAnswer` で文字列比較（LLM不要）
- 記述問題: LLMClient.GradeAnswer()に採点委譲（模範解答との意味的類似度で判定）
選択問題でLLMを呼ぶのはコスト・レイテンシの無駄なので分岐する。

## 重複回答ポリシー
同一 (user_id, question_id) の再解答は上書き（Upsert）。
answer_count/correct_countは再解答でも必ずインクリメント（解答試行の累積カウント）。
再解答を禁止すると学習の反復練習ができなくなるため上書き方式を採用。

## トランザクション境界と責務分担
トランザクションは使わない。
- Upsert（answers書き込み）: 単体でアトミック
- IncrementStats（questions統計更新）: 単体でアトミック
統計の多少のズレ（例: Upsert成功後にIncrementStatsが失敗）は許容範囲。
整合性より可用性・シンプルさを優先する。LLMをトランザクション内に入れるデメリットが大きい。
