# AI Learning Platform Setup Rationale

## Directory Structure and Clean Architecture

The backend layout separates domain, use case, repository, handler, and middleware concerns so that the core business model stays independent from delivery and infrastructure details. `cmd` contains the executable entrypoint, while `internal` keeps implementation details private to the module. This structure supports incremental growth from a minimal API into a larger service without forcing early coupling between HTTP, persistence, and business rules.

The frontend uses a lightweight feature foundation with separate directories for components, pages, hooks, theme, types, and API access. That keeps UI composition, routing, shared design tokens, and server communication distinct from one another. The `reasoning` directory preserves architecture decisions and tradeoff notes in-repo so future changes can reference the original setup assumptions.

## Why sqlc Instead of GORM

`sqlc` was selected over GORM because this platform has a relational data model with explicit joins, counters, feed queries, and analytics-oriented access patterns. Generated typed query code keeps SQL visible and reviewable, avoids ORM abstraction leaks, and makes query performance easier to reason about early.

For this domain, explicit SQL is a better fit than active-record-style mutation because question generation, answer tracking, timelines, and social interactions tend to produce custom reads. `sqlc` also aligns better with Clean Architecture because repository interfaces can sit above generated code without pushing ORM models into the domain layer.

## Firebase Auth Selection

Firebase Authentication is a pragmatic choice for initial launch because it reduces the amount of custom identity infrastructure required while still supporting secure token verification on the Go backend. It provides a fast path to email, Google, and other provider sign-in flows, which is useful for a student-focused product where onboarding friction matters.

This approach also keeps authentication concerns separate from the application user profile stored in PostgreSQL. Firebase manages identity and session primitives, while the local `users` table stores platform-specific profile and subscription attributes.

## Timeline Recommendation Logic with Scoring

The timeline should rank candidate posts using a weighted score rather than pure recency. A practical starting formula is:

`score = recency_weight + interest_match_weight + relationship_weight + engagement_weight + learning_value_weight`

- `recency_weight`: favors new content with time decay.
- `interest_match_weight`: boosts posts linked to followed fields, saved books, and declared user interests.
- `relationship_weight`: boosts followed users and high-affinity creators.
- `engagement_weight`: uses likes, reposts, comments, and answer activity with dampening to avoid runaway popularity bias.
- `learning_value_weight`: boosts posts containing high-signal educational artifacts such as explanations, notes, highlights, or well-performing questions.

An initial scoring recommendation is 35% recency, 25% interest match, 15% relationship, 15% engagement, and 10% learning value. This keeps the feed fresh while still personalizing around study relevance rather than pure social popularity.

## Index Design Rationale

The initial indexes target expected high-frequency access paths:

- `posts(created_at DESC)` supports recent feed retrieval.
- `posts(book_id)`, `posts(field_id)`, and `posts(user_id)` support scoped feeds and profile lookups.
- `follows(follower_id)` and `follows(followee_id)` support social graph reads in both directions.
- `answers(user_id)` and `answers(question_id)` support learning history and question analytics.
- `highlights(user_id)` and `highlights(book_id)` support personal library and book context retrieval.

This is intentionally conservative. It covers clear read patterns without over-indexing write-heavy tables before production traffic reveals additional hotspots.

## Local Docker Compose Design

The development compose file prioritizes local iteration: PostgreSQL 16 with a health check, a Go backend exposed on port 8080, and a frontend exposed on port 3000. Production deployment is Cloud Run + Neon PostgreSQL, so Docker Compose is a local development convenience rather than the production topology.

Keeping local PostgreSQL on the same major version as Neon reduces schema drift while preserving fast local setup.

## AI Model Design

For AI-assisted generation, `gemini-2.5-flash` is the default model for the free tier. It is suitable for bounded question generation where latency and cost matter.

For paid plans or premium generation flows, `gemini-2.5-pro` is the better option when higher-quality explanations, more nuanced reasoning, and better multi-step synthesis are required. A practical product split is:

- Free tier: `gemini-2.5-flash` for bounded generation tasks and faster responses.
- Paid tier: `gemini-2.5-pro` for deeper explanations, higher-quality adaptive questions, and richer note analysis.

The model selection is exposed through the `domain.LLMClient` interface so usecase code does not import the Gemini infrastructure package directly.
