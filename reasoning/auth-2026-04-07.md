# Firebase Auth 認証基盤 設計根拠

## 何を作ったか
Firebase Admin SDKを使ったJWT検証ミドルウェアとユーザー管理APIをClean Architectureで実装した。

## 認証フロー
1. FrontendでFirebase Auth SDKを使ってログイン → IDトークン取得
2. BackendへリクエストのたびにAuthorizationヘッダにBearerトークンを付与
3. BackendのFirebase Adminミドルウェアでトークンを検証
4. 検証後、firebase_uidをecho.Contextにセットして後続ハンドラへ

## なぜFirebase Authか
- 自前JWT実装はセキュリティリスクが高い（鍵管理・ローテーション・リプレイ攻撃など）
- Firebase Authはそれらを全て抽象化し、Google/Apple/GitHubのOAuthも無料で利用可能
- グローバル対応（多言語メール確認、電話番号認証）が不要な設定追加で可能
- バックエンドはVerifyIDTokenのみに集中できる

## Clean Architecture適用
- domain/user.go: DBに依存しない純粋なGoの構造体
- repository/interface: テスト時にモック実装を差し替えられる
- usecase/user_usecase.go: ビジネスロジック（upsert方式のサインアップ）
- handler/user_handler.go: HTTPの入出力のみ担当

## サインアップのupsert設計
Firebase UIDが既存なら既存ユーザーを返し、なければ作成する。
これにより、トークン更新後の再サインアップや複数デバイスからのサインアップが冪等になる。

## 却下した選択肢
- JWT自前実装: セキュリティリスクが高く、期限・署名検証の責任が増える
- セッションCookie方式: SPAとの相性が悪く、クロスドメインでの利用に制限がある
- Supabase Auth: Firebase Authと機能は同等だが、本プロジェクトはGCP(Firebase)で統一する方針のため採用しなかった
