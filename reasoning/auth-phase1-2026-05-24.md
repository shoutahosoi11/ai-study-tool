# Auth Phase 1: Firebase Session Cookie + CSRF Defense

## 何を作ったか

- `POST /api/v1/auth/session` を追加し、Firebase ID token から Firebase Session Cookie と CSRF token を発行するようにした。
- `POST /api/v1/auth/refresh` を追加し、既存 Session Cookie と fresh ID token の UID 一致を確認して Session Cookie をローテーションできるようにした。
- `POST /api/v1/auth/logout` で現在のブラウザ/デバイスの auth cookie を削除できるようにした。
- `POST /api/v1/auth/logout-all` で Firebase `RevokeRefreshTokens` を呼び、全デバイスの session を revoke できるようにした。
- Session Cookie 認証、CSRF double submit、Bearer/Session ハイブリッド認証、セキュリティヘッダーの middleware を追加した。
- Firebase Admin SDK の session cookie 操作は `internal/infrastructure/firebase` に閉じ込め、middleware/handler は `domain.SessionCookieManager` / `domain.SessionVerifier` に依存する形にした。
- CORS を `ALLOWED_ORIGINS` ベースに移行し、credentials と `X-CSRF-Token` header を許可した。

## なぜこの設計か

- ハイブリッド期間中に既存 Bearer クライアントを壊さないため、Session Cookie がある場合だけ Session 経路を優先し、Cookie がなければ従来の Bearer middleware に委譲する。
- CSRF は unsafe method かつ Session Cookie が存在する request にだけ強制する。これにより Cookie 認証では double submit cookie pattern を適用しつつ、Bearer-only の既存 mobile/extension/web client は移行前でも動き続ける。
- `__Host-session` は production/staging 系で使い、`APP_ENV=development` では local HTTP 開発のため `session` cookie + `Secure=false` に落とす。
- `SESSION_COOKIE_DOMAIN` は development cookie のみで使い、`__Host-` prefix の制約を壊さないため production cookie には Domain を付けない。
- Session Cookie は Firebase 公開鍵検証と revoke check に委ねるため、Cloud Run 側に server session store を持たずステートレスに保つ。
- `auth_time` が5分以内の ID token だけ session 化することで、古い ID token の漏洩リプレイを抑える。

## 他の選択肢

- CSRF middleware を全 unsafe API に無条件適用する案もあったが、Bearer-only 既存クライアントが即座に壊れるため Phase 1 では採用しなかった。完全移行後に Bearer 経路を削除するタイミングで厳格化できる。
- refresh endpoint を Session Cookie だけで再発行する案は、Firebase Admin SDK の `SessionCookie` が ID token を入力に取るため採用しなかった。Phase 1 では既存 Session Cookie の UID と fresh ID token の UID 一致を確認してローテーションする。
- Firebase SDK 型を middleware/handler に直接渡す案もあったが、Clean Architecture の依存方向を守るため domain に小さな token/interface を置き、Firebase SDK 依存を infrastructure に寄せた。
- `ALLOWED_ORIGINS` のみに完全移行する案もあったが、既存 deploy config の互換性を考えて `CORS_ALLOWED_ORIGINS` も fallback として残した。
